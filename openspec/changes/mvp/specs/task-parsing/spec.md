# Парсинг задач

## Purpose

Разбор свободного текста через LLM с промежуточным редактированием. После подтверждения создаются самостоятельные задачи без вложенных подзадач.

## ADDED Requirements

### Requirement: REQ-TP-1 — AI Parse запрос

Система SHALL принимать `{ "rawText": string }` длиной 1–500 символов после trim и создавать серверный черновик со статусом PENDING и TTL 30 минут.

#### Scenario: Черновик создан

- **WHEN** отправлен `POST /api/boards/:slug/tasks/parsed`
- **THEN** после валидного ответа LLM сервер возвращает 201:
  ```json
  {
    "draftId": "draft-id",
    "parsedFields": {
      "title": "Подготовка релиза",
      "priority": "high",
      "dueDate": "2026-11-20",
      "tags": ["release", "planning"],
      "subTasks": [{ "title": "Согласовать релиз с Аней" }, { "title": "Подготовить ченджлог" }]
    },
    "expiresAt": "2026-11-17T12:30:00.000Z"
  }
  ```
- **AND** черновик связан с доской и `clientId` инициатора

#### Scenario: Некорректный ввод

- **WHEN** rawText пустой или длиннее 500 символов
- **THEN** сервер возвращает 400, не вызывая LLM

#### Scenario: LLM недоступна

- **WHEN** исчерпаны максимум две попытки вызова при timeout, network error, 5xx или невалидном ответе
- **THEN** сервер возвращает 503 `{ "error": "Не удалось разобрать задачу. Создайте вручную." }`
- **AND** клиент показывает toast и кнопку ручного создания, сохраняя исходный текст

### Requirement: REQ-TP-2 — Нормализация ответа LLM

Сервер SHALL проверять JSON-схему ответа и MUST NOT выполнять инструкции из пользовательского текста. API-ключ и модель задаются серверной конфигурацией; пользовательский ввод передаётся отдельным user message.

#### Scenario: Подзадачи нормализуются

- **WHEN** LLM вернула более 10 непустых подзадач
- **THEN** сохраняются первые 10 и клиент показывает «Усечено до 10 подзадач»
- **AND** 0–1 подзадача сохраняется для предпросмотра, но при финализации не создаёт отдельных задач

#### Scenario: Обязательные и необязательные поля

- **WHEN** title отсутствует или пуст
- **THEN** ответ считается невалидным и запускается повторная попытка с описанием ошибки
- **AND** неизвестный/отсутствующий priority заменяется на `medium`, невалидный dueDate — на `null`, tags фильтруются по ограничениям задачи

#### Scenario: Безопасность и наблюдаемость

- **WHEN** выполнен вызов LLM
- **THEN** логируются попытка, latency и token usage без API-ключа и rawText
- **AND** максимальный размер ответа и timeout ограничены сервером

### Requirement: REQ-TP-3 — Просмотр и редактирование черновика

Черновик SHALL быть доступен только клиенту-владельцу по `clientId`; другие участники доски не видят его в board state и не могут изменять по draftId.

#### Scenario: AiPreview открыт

- **WHEN** parse успешен либо страница перезагружена с PENDING-черновиком этого клиента
- **THEN** панель по макету `design/screens/board-add-task.html` показывает редактируемые title, priority, dueDate, tags и subTasks
- **AND** доска под панелью затемнена, повторный parse и submit недоступны

#### Scenario: Сохранение правок

- **WHEN** отправлен `PATCH /api/boards/:slug/drafts/:draftId` с полным `parsedFields`
- **THEN** сервер валидирует title 1–200 символов, 0–10 subTasks и остальные поля задачи, возвращает обновлённый черновик
- **AND** изменения переживают reload, но не обновляют `updated_at` доски

#### Scenario: Черновик недоступен

- **WHEN** черновик DISCARDED, не найден или принадлежит другому clientId, либо истёкший PENDING обрабатывается операцией, отличной от идемпотентного finalize
- **THEN** сервер возвращает 404 и не выполняет операцию

### Requirement: REQ-TP-4 — Финализация черновика

Финализация SHALL атомарно создавать основную задачу и, если в черновике 2–10 элементов subTasks, отдельную задачу для каждого элемента. Все задачи получают статус `todo`, а приоритет, dueDate и tags наследуют от основной. Вложенные связи между задачами не создаются.

#### Scenario: Сохранить на доску

- **WHEN** отправлен `POST /api/boards/:slug/drafts/:draftId/finalize`
- **THEN** создаются либо 1 задача (при 0–1 подзадаче), либо 3–11 задач (при 2–10 подзадачах); черновик становится FINALIZED и `updated_at` доски обновляется один раз
- **AND** идемпотентный finalize допускается для уже FINALIZED-черновика; для ещё PENDING с истёкшим TTL возвращается 404 без создания задач
- **AND** ответ 200 содержит `{ "draftId": "...", "tasks": [...] }`
- **AND** для каждой задачи отправляется `task_created`, затем один `draft_finalized` с полным списком `taskIds`

#### Scenario: Повторная финализация

- **WHEN** повторный запрос от того же clientId находит FINALIZED-черновик
- **THEN** возвращается 200 с ранее созданными задачами
- **AND** новые задачи и SSE-события не создаются

### Requirement: REQ-TP-5 — Отмена и TTL черновика

Отмена SHALL переводить PENDING-черновик в DISCARDED без создания задач. Планировщик раз в минуту отклоняет черновики с истёкшим `expiresAt`.

#### Scenario: Ручная отмена

- **WHEN** отправлен `POST /api/boards/:slug/drafts/:draftId/discard`
- **THEN** сервер возвращает 200 и отправляет владельцу `draft_discarded`

#### Scenario: Истёк TTL

- **WHEN** планировщик обнаруживает PENDING с `expiresAt <= now()`
- **THEN** черновик становится DISCARDED, задачи не создаются
- **AND** отправляется `draft_discarded` с `{ "draftId": "...", "reason": "expired" }`

#### Scenario: Discard после финализации

- **WHEN** отправлен discard для FINALIZED-черновика того же владельца
- **THEN** сервер возвращает 409, задачи и статус не меняются

### Requirement: REQ-TP-6 — Тексты и поведение формы

Форма SHALL использовать тексты макета: «ИИ нарисовал черновик. Поправьте, что нужно», «Название», «Приоритет», «Срок», «Теги», «Подзадачи», «Отмена», «Сохранить на доску». Select priority и native date input используются вместо статичных input макета; чекбоксы у подзадач отсутствуют.

#### Scenario: Редактирование списка

- **WHEN** пользователь изменяет, добавляет или удаляет подзадачу
- **THEN** список остаётся в диапазоне 0–10 непустых элементов
- **AND** «Сохранить на доску» сохраняет правки и финализирует одну последовательную операцию без потери изменений

#### Scenario: Ошибка сохранения

- **WHEN** сохранение, финализация или отмена завершились ошибкой
- **THEN** введённые данные остаются в форме, отображается сообщение и доступен повтор
- **AND** кнопки блокируются на время запроса, предотвращая параллельные submit
